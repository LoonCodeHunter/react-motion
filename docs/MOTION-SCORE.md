# Kovari React Motion — Motion Score

The **Motion Score** is a reproducible, project-specific benchmark index from **0 to 100** for the `@kovari/react-motion` package built from the exact source commit under test. Zero is the lowest possible score; 100 is the highest possible score.

- [Current score badge data](../motion-score.json)
- [Motion Score workflow and historical runs](https://github.com/LoonCodeHunter/react-motion/actions/workflows/motion-score.yml)
- [Benchmark workflow source](../.github/workflows/motion-score.yml)
- [Benchmark implementation](../scripts/motion-score/)

The badge at the top of the README links here. It displays the value stored in `motion-score.json`; it is not calculated by Shields.io. GitHub Actions measures the package, validates the result and then updates the tracked JSON on `main`.

## Score bands

| Score | Shields colour | Interpretation |
|---:|---|---|
| 0–49 | Red | Needs attention; investigate the benchmark summary and component results |
| 50–69 | Yellow | Developing; identify lower-scoring primitive measurements |
| 70–89 | Green | Good within comparable runner/browser conditions |
| 90–100 | Yellow-green | Excellent result for the measured workload |

The score is always an integer in the inclusive range `0–100`. Values below zero are clamped to zero before choosing a colour; values above 100 are clamped to 100. Inputs generated by the live benchmark are validated before writing the public score file.

## Measured components and weights

| Component | Weight | What is measured |
|---|---:|---|
| Frame cadence | 40% | `requestAnimationFrame` cadence during twelve concurrent transform/opacity animations, including frames longer than 24 ms |
| Spring sampling | 20% | Spring sample points generated per second |
| MotionValue throughput | 20% | Numeric `motionValue.set()` operations per second with a subscriber attached; the count of subscriber notifications is validated |
| Animation timing | 20% | Closeness of the median observed completion time to a 96 ms native animation target |

The shared scoring code is in `scripts/motion-score/core.mjs`. Its unit tests cover score bounds, component weights, colour thresholds, invalid metrics and a monotonicity case. If the weights or thresholds change, update the implementation, tests, workflow summary and this document together.

### Normalisation

- Frame score begins at 100 and is penalised when observed FPS falls below 60 or when the measured fraction of frames longer than 24 ms rises.
- Spring score normalises sampling throughput against 150,000 points per second.
- MotionValue score normalises throughput against 200,000 updates per second.
- Animation timing score begins at 100 and decreases in proportion to the absolute deviation from 96 ms.
- Each component is clamped to `0–100`; the weighted result is rounded to an integer and clamped again.

These targets are engineering choices for an internal trend metric, not external industry standards. They should be calibrated against multiple stable runs before being used for public performance comparisons.

## What this score is—and is not

The benchmark is useful for spotting changes in selected primitives on a consistent CI runner. It is **not** a certification or a universal claim that a product will achieve a particular FPS on user devices.

It does not measure all React render costs, layout shifts, energy consumption, mobile GPU performance, accessibility, animation aesthetics, package download size, or every supported browser. Runner contention, Chromium versions and host changes can affect the result. Compare history from the same hosted runner and treat small changes cautiously.

## Workflow lifecycle

1. On a push to `main`, pull request, manual dispatch or weekly schedule, the read-only `benchmark` job builds and packs the exact checked-out source into a local npm tarball, then installs that tarball in an isolated temporary workspace.
2. The workflow installs Chromium, serves a small browser-only benchmark with Vite and collects metrics using Playwright.
3. `score-runner.mjs` applies the shared scoring function and creates a Shields endpoint JSON document with `label`, `message`, and `color` fields.
4. A validation step confirms the package identity, schema version, integer score bounds, allowed colours and component score ranges.
5. The result is uploaded as a `kovari-react-motion-score` artifact and reported in the GitHub Actions job summary.
6. On non-PR runs against `main`, the separate `update-score` job receives `contents: write` and updates `motion-score.json` if it changed. The benchmark job itself has read-only repository permissions.

The `motion-score.json` path is ignored by the push trigger, and the score commit includes `[skip ci]` to minimise redundant runs. If branch protection prevents the GitHub Actions bot from pushing to `main`, the measured result and artifact can still be inspected, but the tracked badge JSON will not update until the repository's permitted update strategy is configured.

## Run it

From GitHub, open **Actions → Motion Score → Run workflow** and choose the default branch. The workflow measures the exact source commit selected by the event. It builds the checked-out source, installs that locally packed tarball in an isolated benchmark workspace, and records both the package version and `GITHUB_SHA` in the score output and job summary.

Local source verification is separate:

```bash
npm ci
npm run typecheck
npm test
npm run pack:verify
npm run pack:dry
npm run release:check
```

These checks validate the source tree and npm package layout; the Motion Score workflow separately benchmarks a local tarball built from the same checked-out source. The release gate uses `npm pack --dry-run`, not `npm publish --dry-run`, because npm 11 can reject a dry run when the current package version already exists on the registry.
